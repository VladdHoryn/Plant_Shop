## 2. Навіщо документація і що таке Documentation as Code

**Документація** — це зафіксоване знання про систему, яке дозволяє людині, що її не писала, зрозуміти, запустити,
змінити та супроводжувати систему **без автора**. Код відповідає на питання «що робить машина»; документація —
на питання «навіщо», «як влаштовано в цілому», «як запускати», «чому саме так».

Головна теза лекції: **застаріла документація небезпечніша за відсутню.** Коли документа немає, інженер знає, що
не знає, і йде читати код. Коли документ є, але бреше, інженер діє впевнено і помиляється: розгортає не в тому
порядку, тестує неіснуючий контракт, пояснює бізнесу поведінку, якої вже немає. Це «ілюзія розуміння».

**Documentation as Code (Docs as Code)** — підхід, за якого документація живе поруч із кодом і проходить ті самі
процеси:

| Практика коду | Те саме для документації | У Plant Shop |
|---|---|---|
| текстовий формат у Git | Markdown, Mermaid замість картинок | `docs/*.md`, діаграми Mermaid |
| code review | рецензія документації в тому самому PR | `.github/pull_request_template.md` |
| CI-перевірки | автоматична перевірка відповідності коду | `docs-currency.yml` → `doc-drift-check.sh` |
| версіонування | історія змін, `git blame`, теги | метрики актуальності з `git log` |
| генерація | документація з коду | Swagger UI (springdoc) |

Перевага: документ і код змінюються одним комітом, тому їх розбіжність видно в diff і можна заблокувати в CI.

## 3. Класифікація: продукт і процес

Це питання зі штрафом −2, тому його треба знати напам'ять.

| | Документація **продукту** | Документація **процесу** |
|---|---|---|
| Що описує | саму систему: що вона робить, як влаштована, як її запускати | як система **створювалася**: плани, рішення в моменті, звіти, протоколи, повідомлення комітів |
| Життєвий цикл | **«жива»**: еволюціонує разом із системою, має бути актуальною **зараз** | **«історична»**: фіксує факт у часі, після створення **не змінюється** |
| Хто споживає | розробники, QA, DevOps, користувачі, бізнес — усі, хто працює з системою | менеджмент, аудитори, викладач, майбутні архітектори (щоб зрозуміти історію) |
| Що буде, якщо не оновлювати | **Documentation Decay** — документ почне брехати | нічого: він і має описувати минуле |
| Приклади в проєкті | `README.md`, `docs/sdd.md`, `docs/isd.md`, ADR (як чинні рішення), Swagger, Javadoc, коментарі `docker-compose.yml`, workflow-файли | `docs/lab-08-report.md`, `docs/k8s-report.md`, `docs/privacy-demo.md`, тексти завдань `docs/lab-0N.md`, повідомлення комітів |

Тест для захисту: **«Чи має цей документ змінитися, якщо завтра зміниться код?»** Так → продукт. Ні, бо він
описує стан на певну дату → процес.

Цікаві граничні випадки:
- **ADR** — запис про рішення в момент його ухвалення (як процес), але чинний ADR описує поточну архітектуру (як
  продукт). Тому ADR не переписують (процесна природа), але змінюють **статус** (`Superseded`), щоб набір ADR
  описував поточний стан (продуктна природа).
- **Повідомлення коміту** — процес: описує зміну в момент коміту; переписувати історію не можна.
- **Звіт про приватність** — процес, але в ньому опинилися знання продукту (правила стирання). Це «темна зона»:
  знання є, але не в тому типі документа, де їх шукатимуть.
- **Javadoc «Lab 8, task 3: ...»** — історія процесу, що протекла в документацію продукту. Вердикт — прибрати.

Класифікація за Соммервіллем (I. Sommerville, «Software Documentation»): документація процесу (плани, звіти,
стандарти, робочі записи) і документація продукту, яка ділиться на **користувацьку** (для тих, хто використовує
систему) і **системну** (для тих, хто її супроводжує: архітектура, вимоги, код, тести, інструкції).

## 5. Метрики актуальності

### 5.1. Три індикатори з завдання

| Метрика | Команда | Поріг | Що означає |
|---|---|---|---|
| **Last Updated Age** — вік останнього оновлення | `git log -1 --format=%cs -- <файл>` → дні до дати аудиту | > 90 днів — підозрілий, > 180 — ймовірно застарілий | як давно документ хтось торкався |
| **Code-Doc Change Ratio** — співвідношення змін коду і документа | `git log --oneline -- src/<компонент> \| wc -l` проти `git log --oneline -- <документ> \| wc -l` | > 20 змін коду без жодного оновлення документа — структурний дрейф | код утік уперед від документа |
| **Access Evidence** — свідчення використання | питання колег, посилання в задачах, чаті; у нас — `git grep` посилань і зміни за 30 днів | немає споживача → Dead Documentation | чи потрібен документ комусь |

### 5.2. Похідна метрика lag, яку я додав

`lag = git log --oneline <останній коміт документа>..HEAD -- <код, який він описує> | wc -l` — кількість
комітів коду **після** останнього оновлення документа. Це точніша версія Code-Doc Change Ratio: ratio рахує всю
історію, lag — лише те, що документ «пропустив». Поріг завдання (> 20) застосовано саме до lag.

### 5.3. Обмеження метрик (важливо сказати на захисті)

- **Метрики — це сигнал, а не доказ.** Свіжий документ може брехати (README Plant Shop мав вік 20 днів, але
  помилкове «saga orchestration»), а старий — бути правдою (ADR про рішення 2-річної давності).
- **Вік — запізнілий індикатор.** У краш-тесті FAIL і PASS були в один день — вік лишився 0, а lag одразу
  показав 1. Тому для швидких змін потрібні lag і автоматична перевірка відповідності.
- **Молодий репозиторій.** Проєкту 31 день: поріг 90 днів фізично недосяжний. Пороги я **не підганяв**, а довів
  decay звіркою тверджень з кодом (`claim-verification.txt`).
- **Access Evidence у соло-проєкті** не має чату й трекера, тому використано проксі: вхідні посилання і зміни.
- **Документи процесу** не мають lag (`n/a`): вони не зобов'язані йти за кодом.

## 6. Антипатерни: Documentation Decay і Dead Documentation

| | Documentation Decay (деградація, «гниття») | Dead Documentation (мертва документація) |
|---|---|---|
| Визначення | документ **описує систему, якої вже немає** | документ **існує, але не має споживача** |
| Головна шкода | хибні рішення через довіру до неправди | марні витрати на супровід; «шум», за яким губляться живі документи; рано чи пізно теж стає Decay |
| Як виявити | звірити твердження документа з кодом; lag > 0; автоматичні перевірки (drift check) | немає вхідних посилань, ніхто не помітив очевидної помилки, немає змін і звернень |
| Приклад у Plant Shop | README: «saga orchestration» (в коді хореографія); README і k8s без user-service; CLAUDE.md «Current lab: Lab 8» | `helm-report.md` обірваний 30 днів, і ніхто не помітив; `lab-9.md` без жодного посилання |
| Типові ліки | оновити; правило «зміна коду = зміна документації»; CI-перевірка | видалити або позначити deprecated; або зробити досяжним (посилання) |

Причини Decay: документацію пишуть «один раз» в кінці проєкту; немає власника; зміна коду не вимагає зміни
документа; документ далеко від коду (wiki), тому його не видно в diff.

Споріднені антипатерни: **Tribal Knowledge** (знання лише в головах), **Write-only documentation** (пишуть для
звітності, не читає ніхто), **Documentation Hell** (документів так багато, що потрібне не знайти),
**Copy-paste docs** (той самий текст у кількох місцях розходиться після першої зміни).

## 7. Вердикти аудиту: оновити, видалити, deprecated

| Вердикт | Коли | Приклад у проєкті |
|---|---|---|
| **Оновити** | документ потрібний, але містить неправду або прогалини | README (D1, D3, D4), CLAUDE.md, Javadoc |
| **Видалити** | документ не має цінності і не є історичним записом, який треба зберегти | речення Javadoc «Since Lab 8 (FAIL commit)...» — чиста історія процесу в коді продукту |
| **Deprecated** | документ вводить в оману щодо поточної системи, але є цінним історичним записом або на нього є посилання | `k8s-report.md`, `helm-report.md`: банер «DEPRECATED» + посилання на ISD, зміст не змінюється |
| Залишити | документ актуальний або це коректний запис процесу | `docker-compose.yml`, звіти лабораторних |

Чому не просто видалити старий звіт: документацію процесу **не знищують** — вона пояснює, як система дійшла до
поточного стану. Deprecated зберігає історію і водночас попереджає читача.

## 8. SDD і ISD: у чому різниця

Друге питання зі штрафом −2.

| | **SDD — System Design Document** | **ISD — Infrastructure Specification Document** |
|---|---|---|
| Головне питання | **ЯК система влаштована всередині** | **ДЕ і НА ЧОМУ система працює** |
| Рівень | логічна архітектура | фізична / експлуатаційна архітектура |
| Зміст | контекст, C4 контейнерів, компоненти і їх відповідальність, залежності, модель даних (ER), API- і подієві контракти, наскрізні рішення | топологія розгортання, середовища dev/test/prod, змінні оточення (без секретів), порядок запуску, сховища, CI/CD (стадії, тригери, quality gates), реліз і відкат, моніторинг, backup з RTO/RPO, ризики |
| Головна аудиторія | розробники, QA | DevOps |
| Змінюється, коли | з'являється компонент, контракт, таблиця | змінюється розгортання, конфігурація, конвеєр |
| Приклад з Plant Shop | «order-service читає платіж через Feign `PaymentClient`» | «order-service стартує в 4-й хвилі після healthy payment-service» |
| Стандарти | IEEE 1016 (Software Design Description), arc42 розд. 5 (Building Block View) | arc42 розд. 7 (Deployment View), ISO/IEC/IEEE 42010 — опис архітектури загалом |

Як не переплутати: **SDD можна читати, не знаючи, де система запущена; ISD можна виконувати, не знаючи, як
влаштований код.** Обидва посилаються один на одного: кожен компонент SDD → його розгортання в ISD.

Третій компонент паспорта — **ADR: ЧОМУ** обрано саме таку будову (розділ 10).

## 9. Модель C4

Автор — Simon Brown. Чотири рівні масштабу, як мапа з різним наближенням:

| Рівень | Що показує | Хто читає | У Plant Shop |
|---|---|---|---|
| 1. **Context** | система як «чорна скринька», люди і зовнішні системи | усі, включно з бізнесом | SDD 1: покупець, персонал, поштовий провайдер |
| 2. **Container** | окремо розгортані/запускані частини: застосунки, БД, черги | розробники, архітектори, DevOps | SDD 2: 8 сервісів, Kafka, 5 БД |
| 3. **Component** | компоненти всередині одного контейнера | розробники модуля | SDD 3 (текстом): контролер → сервіс → репозиторій, `OrderTrackingService` |
| 4. **Code** | класи, UML | рідко; краще генерувати з IDE | не створювався |

Важливо: **«контейнер» у C4 ≠ Docker-контейнер.** Це будь-яка одиниця, що виконується окремо (застосунок, БД,
браузерний застосунок). Бібліотека `secure-logging` — не контейнер, бо не запускається окремо.

Mermaid підтримує синтаксис `C4Context` і `C4Container` (`Person`, `System`, `Container`, `ContainerDb`,
`ContainerQueue`, `System_Boundary`, `Rel`) — рендериться в GitHub і Obsidian.

## 10. ADR — Architecture Decision Records

**ADR** — короткий документ, що фіксує одне значуще архітектурне рішення: контекст, альтернативи, вибір і
наслідки. Формат запропонував Michael Nygard (2011). Набір ADR — «кущ» рішень, історія того, чому система така.

Шаблон (як у `docs/architecture/adr/README.md`):

| Поле | Зміст |
|---|---|
| Номер і назва | `ADR-0002: Сага замовлення як хореографія подій Kafka` |
| Статус | Proposed → Accepted → (Deprecated / Superseded by ADR-NNNN) |
| Контекст | проблема і сили: вимоги, обмеження |
| Розглянуті альтернативи | варіанти з перевагами і недоліками |
| Рішення | що обрано і які правила з цього випливають |
| Наслідки | позитивні, негативні, обмеження для розробників |

**Правило незмінності:** ADR фіксується в момент рішення і **ніколи не переписується заднім числом**. Якщо
рішення змінилось — пишемо новий ADR з новим номером, а старому змінюємо лише статус на `Superseded by ADR-NNNN`.
Інакше губиться головна цінність — історія «чому», і новий архітектор може повернутися до вже відкинутої
альтернативи.

У проєкті:
- ADR-0001 — окрема PostgreSQL на сервіс + Flyway (альтернативи: спільна БД, схеми в одній БД, NoSQL, `ddl-auto`).
- ADR-0002 — хореографія саги на Kafka (альтернативи: синхронний ланцюжок REST, 2PC, оркестрація, RabbitMQ).
- ADR-0003 — синхронне читання платежу для трекінгу. Він **доповнює**, а не замінює ADR-0002, тому в ADR-0002
  змінено лише рядок статусу: `Accepted (доповнено ADR-0003)`.

**Хореографія vs оркестрація** (часте питання): в оркестрації центральний сервіс надсилає учасникам команди і
керує станом процесу; у хореографії центру немає — кожен учасник реагує на події інших. Plant Shop — хореографія:
payment-service сам слухає `inventory-reserved`, ніхто йому не наказує.

## 11. RTO і RPO

| | **RPO — Recovery Point Objective** | **RTO — Recovery Time Objective** |
|---|---|---|
| Питання | **скільки даних** (за часом) допустимо втратити? | **як швидко** система має знову працювати? |
| Дивиться | **назад** від моменту збою — до останньої копії | **вперед** від моменту збою — до відновлення |
| Визначається | частотою резервного копіювання / реплікації | процедурою відновлення, автоматизацією, людьми |
| Plant Shop (order-db) | 24 год (щоденний `pg_dump`) | 1 год |

Приклад: копія щоночі о 02:00, збій о 18:00 → втрачено до 16 год даних (≤ RPO 24 год — ціль виконана).
Відновлення тривало 40 хв → RTO 1 год виконано.

Як обирають: що критичніше для бізнесу, то менші RPO/RTO і дорожче рішення (реплікація, WAL-архівування, PITR
замість щоденного dump). Kafka в Plant Shop не копіюється: події — лише транспорт, стан саги зберігається в
БД сервісів.

Важливо: **резервна копія, з якої ніхто не пробував відновитися, — не копія.** Тому в ISD процедуру перевірено
тренуванням (`backup-drill.txt`: dump 0,49 с, restore 0,42 с, 10 з 10 рядків).

## 12. Матриця покриття аудиторій

Матриця `Аудиторія | Ключові питання | Документ-відповідь | Статус` перевіряє, що паспорт обслуговує всіх, а не
лише автора. Як будувати:
1. Для кожної аудиторії сформулювати 2–3 питання, які вона реально ставить.
2. Для кожного питання знайти документ і розділ, що відповідає **без читання коду**.
3. Нема відповіді — **прогалина**; є частково — «частково»; закрити прогалини на практиці.

У Plant Shop: до паспорта з 15 питань покрито 1, частково 7, прогалин 7; після — 15 з 15. Найбільші прогалини
були в бізнесу («що система робить?» — README починався з таблиці портів) і QA (контракти були лише для 9 з 27
ендпоінтів).

## 13. Супровід документації

**Регламент підтримки (Documentation Maintenance Regime)** — правила, що роблять документацію об'єктом
безперервного супроводу, а не разовим артефактом:

| Елемент | Зміст | У проєкті |
|---|---|---|
| Власник (owner) | конкретна людина, відповідальна за актуальність | VladdHoryn; заступник — вакантно |
| Цикл перегляду (review_date) | експлуатаційна — щонайменше раз на 90 днів, архітектурна — раз на 180 (пороги з метрик) | таблиця в `docs/maintenance.md` |
| Тригери позачергового перегляду | які зміни коду вимагають оновлення яких документів | таблиця «Змінено в коді → Оновити» |
| Правило | **«зміна коду = зміна документації»**: злиття без оновлення зачеплених документів не проходить | CI `doc-drift` + чекліст PR |
| Процедура перегляду | drift check → currency report → звірка тверджень → оновлення дати | розділ 4 регламенту |

Чому цикл залежить від категорії: експлуатаційна документація описує те, що змінюється часто (конфігурація,
розгортання), і помилка в ній одразу ламає роботу — тому 90 днів. Архітектура змінюється рідше — 180 днів.

Що можна автоматизувати, а що ні: скрипт перевіряє **факти** (є ендпоінт у SDD? збігається порядок запуску?),
але не **зміст** (чи правильно пояснено, навіщо компонент). Тому потрібні обидва рівні: CI і людина-рецензент.
Це аналог Definition of Done: «задача не виконана, доки не оновлено документацію».

## 15. Handover, Bus Factor, single point of knowledge

**Handover Package** — мінімальний набір, щоб інша команда могла прийняти систему на супровід:
1. реєстр документів паспорта з власниками і статусом актуальності;
2. інструкція онбордингу (3–5 кроків від README до локального запуску, з перевіркою кожного кроку);
3. декларація Bus Factor і план усунення single points of knowledge;
4. відомі ризики і вердикт готовності.

**Bus Factor (Truck Factor)** — мінімальна кількість учасників, після втрати яких («потрапили під автобус»)
проєкт зупиняється, бо ніхто не розуміє критичної частини. Наближена оцінка за Git: скільки авторів мають
суттєвий внесок у кожен модуль (`git shortlog -sn -- <модуль>`); Bus Factor системи — мінімум по критичних
модулях. Відомий алгоритм — Avelino et al. (2016): рахує «авторство» файлів і прибирає найбільших авторів, доки
понад 50 % файлів не залишаться без автора.

**Single point of knowledge** — компонент, який розуміє лише одна людина. **Темна зона** — знання, яке не
записане в документації продукту (є лише в голові, у коді або у звіті процесу).

Оцінка ризику: ризик = ймовірність (P), що наступник не відновить знання × вплив (I) втрати, шкала 1–3.
У Plant Shop: Bus Factor = 1 скрізь; найвищий ризик 9 — правила стирання user-service (знання лише у звіті
процесу `privacy-report.md`).

Як усувати: **парне володіння** (backup owner рецензує кожен PR), **документування темних зон** у документах
продукту, ротація задач, сесії передачі знань, runbook-и для аварій.

**«Always Ready to Handover»** — стан, коли систему можна передати будь-якого дня без підготовки: документація
актуальна і перевіряється автоматично, онбординг відтворюваний, і **немає знань, що належать одній людині**.
Вердикт Plant Shop: «Ready to Handover with conditions» — документація готова, але Bus Factor = 1.

## 17. Питання та відповіді для захисту

**1. Чим документація продукту відрізняється від документації процесу?**
Продукт описує систему і має бути актуальним зараз («живий»); процес фіксує, як систему створювали, на певну
дату («історичний») і не змінюється. Тест: якщо завтра зміниться код, документ має змінитись? Так — продукт.
README і SDD — продукт; звіт лабораторної і повідомлення коміту — процес.

**2. Чим SDD відрізняється від ISD?**
SDD — як система влаштована всередині (компоненти, зв'язки, дані, контракти), для розробників і QA. ISD — де і на
чому вона працює (середовища, розгортання, CI/CD, моніторинг, backup), для DevOps. SDD читається без знання
інфраструктури, ISD виконується без знання коду.

**3. Навіщо ADR, якщо є SDD?**
SDD каже «що є», ADR — «чому саме так і що відкинули». Без ADR новий архітектор може повернутися до відкинутої
альтернативи, не знаючи, чому її відкинули.

**4. Чому ADR не можна редагувати?**
Бо це запис рішення в момент ухвалення з тодішнім контекстом. Нове рішення — новий ADR; старий отримує статус
`Superseded by ADR-NNNN`. Так зберігається історія еволюції архітектури.

**5. Що таке Documentation Decay? Приклад з проєкту.**
Документ описує систему, якої вже немає. README називав order-service «saga orchestration», а в коді
хореографія (8 `@KafkaListener`, payment сам слухає `inventory-reserved`). README і k8s не знали про user-service.

**6. Що таке Dead Documentation? Приклад.**
Документ без споживача. `helm-report.md` 30 днів був обірваним після першого кроку, і цього ніхто не помітив —
доказ, що його не читали. `lab-9.md` не мав жодного вхідного посилання.

**7. Чому застаріла документація гірша за відсутню?**
Відсутність документа видно — інженер іде читати код. Застарілий документ створює ілюзію розуміння: інженер
впевнено діє за неправдою (розгортає в іншому порядку, тестує неіснуючий контракт).

**8. Як ви рахували Last Updated Age?**
`git log -1 --format=%cs -- <файл>` дає дату останнього коміту; віднімаю від дати аудиту 2026-11-14. README:
2026-10-25 → 20 днів.

**9. Що таке Code-Doc Change Ratio і що таке lag?**
Ratio — кількість комітів коду компонента проти комітів документа. Lag — кількість комітів коду після останнього
коміту документа (`git log <останній коміт документа>..HEAD -- <код> | wc -l`). Поріг: > 20 — структурний дрейф.

**10. Жоден документ не перевищив 90 днів і lag 20. Як тоді доведено Decay?**
Репозиторію 31 день, пороги фізично недосяжні, і я їх не змінював. Decay доведено звіркою тверджень з кодом
(`claim-verification.txt`), а метрики працювали як ранній сигнал: обидва документи з lag > 0 (README 7,
CLAUDE.md 8) справді містили неправду.

**11. Чому в краш-тесті вік не зріс, а lag зріс?**
Вік — запізнілий індикатор: FAIL і PASS в один день. Lag реагує на перший же коміт коду без документа (0 → 1).

**12. Що саме ви змінили у FAIL-коміті і чому це валідний краш-тест?**
Новий ендпоінт `/api/orders/{id}/tracking`, новий компонент і Feign-залежність order → payment, змінений
порядок запуску в Compose. Документи не змінювались. Тести зелені — отже, звичайний CI дрейфу не бачить, а
документ бреше трьом групам аудиторій.

**13. Як ви довели дрейф для кожної аудиторії?**
Новачок/бізнес: README «two separate requests» і 0 згадок трекінгу. Розробник/QA: у SDD 0 згадок
`OrderTracking`/`PaymentClient`, C4 без стрілки order → payment. DevOps: рядок ISD про order-service має 4
залежності, `docker compose config` — 5.

**14. Як працює `doc-drift-check.sh`?**
(1) витягує з контролерів усі `@RequestMapping` + `@GetMapping/...` і шукає кожен `METHOD /path` у SDD;
(2) публічні `/api/**` — у README; (3) бере `depends_on` з `docker compose config` (YAML-якорі вже розгорнуті)
і порівнює з таблицею запуску ISD. Будь-яка розбіжність → exit 1 → червоний CI.

**15. Що скрипт не може перевірити?**
Зміст і правильність пояснень, діаграми, ADR, RTO/RPO. Для цього — чекліст PR і рецензент.

**16. Що таке C4? Чим контейнер C4 відрізняється від Docker-контейнера?**
Чотири рівні: Context, Container, Component, Code. Контейнер C4 — будь-яка окремо запускана одиниця (сервіс, БД,
черга), не обов'язково Docker. Бібліотека `secure-logging` — не контейнер.

**17. Що таке RTO і RPO? Які значення у вас і чому?**
RPO — скільки даних допустимо втратити (24 год: щоденний dump), RTO — за який час відновитися (1 год для
замовлень/платежів/користувачів, 2 год для каталогу/складу). Фінансові й персональні дані критичніші.

**18. Звідки впевненість, що backup працює?**
Тренування: тимчасовий PostgreSQL 16 із міграціями catalog → `pg_dump` → `DROP SCHEMA` → `pg_restore` → 10 з 10
рослин (`backup-drill.txt`). Чесно задокументовано, що розкладу копіювання ще немає (ризик R2).

**19. Чому експлуатаційна документація переглядається частіше за архітектурну?**
Вона описує те, що змінюється часто (конфігурація, розгортання), і помилка в ній одразу ламає запуск: 90 днів.
Архітектура стабільніша: 180 днів.

**20. Що таке «зміна коду = зміна документації» і як ви це забезпечили?**
Злиття в master без оновлення зачеплених документів заборонене. Забезпечено CI job `doc-drift`
(`docs-currency.yml`), звітом актуальності в Step Summary і чеклістом у шаблоні PR.

**21. Що таке Bus Factor і який він у вас?**
Мінімальна кількість людей, втрата яких зупиняє проєкт. У Plant Shop = 1: у кожному модулі один автор
(`bus-factor.txt`).

**22. Чи система «Always Ready to Handover»?**
Ні — «Ready with conditions». Документи актуальні й перевіряються CI, онбординг відтворюваний, але Bus Factor = 1
і дві темні зони (правила приватності, конвеєр якості) не описані в документації продукту.

**23. Як усунути single point of knowledge?**
Парне володіння (backup owner рецензує PR), документування темних зон у документах продукту, сесії передачі
знань, ротація задач.

**24. Що таке матриця покриття аудиторій і що вона показала?**
Аудиторія × ключові питання × документ-відповідь × статус. До паспорта: 1 покрито, 7 частково, 7 прогалин з 15;
після — 15 з 15.

**25. Чому звіти лабораторних не оновлюються, а позначаються deprecated?**
Це документація процесу — запис факту в часі. Переписати — означає знищити історію. Банер DEPRECATED із
посиланням на актуальний документ зберігає історію і попереджає читача.

**26. Чому коміти без змісту не виправлені?**
Виправлення вимагає переписування історії (`rebase`), що заборонено правилами роботи: історія комітів оцінюється.
Висновок аудиту — правило Conventional Commits для всіх нових комітів (зараз 19 з 28 = 67,9 %).

**27. Яку реальну проблему інфраструктури знайшов аудит?**
R1 — user-service відсутній у k8s/Helm; R5 — `scripts/quality-gate.sh` у Git без біта виконання, а workflow
викликає його як `./scripts/...` — на Linux буде `Permission denied`.

## 18. Словник термінів

| Термін | Значення |
|---|---|
| Documentation as Code | документація в текстових форматах у Git, з review і CI, як код |
| Документація продукту / процесу | описує систему (жива) / описує процес створення (історична) |
| SDD | System Design Document — внутрішня будова системи |
| ISD | Infrastructure Specification Document — середовище виконання і експлуатація |
| ADR | Architecture Decision Record — запис одного архітектурного рішення |
| C4 | модель архітектурних діаграм: Context, Container, Component, Code |
| Documentation Decay | документ описує систему, якої вже немає |
| Dead Documentation | документ без споживача |
| Last Updated Age | вік останнього оновлення документа |
| Code-Doc Change Ratio | співвідношення змін коду і документа |
| Lag | комітів коду після останнього оновлення документа |
| Access Evidence | свідчення, що документ використовують |
| Structure drift | структура і контракти в документі не збігаються з реальними |
| RPO | допустима втрата даних (за часом) |
| RTO | допустимий час відновлення |
| Owner / review cycle | власник документа / період обов'язкового перегляду |
| Handover Package | пакет передачі системи команді супроводу |
| Bus (Truck) Factor | мінімум людей, втрата яких зупиняє проєкт |
| Single point of knowledge | знання, яке має лише одна людина |
| Темна зона | знання, не записане в документації продукту |
| Хореографія / оркестрація саги | учасники реагують на події без центру / центральний сервіс надсилає команди |
