# ADR-0001: Окрема база PostgreSQL на кожен сервіс, схема лише через Flyway

## Контекст

Магазин складається з п'яти бізнес-сервісів з різними даними: каталог (часто читається), склад (конкурентні
оновлення залишків), замовлення і платежі (фінансові записи), користувачі (персональні дані під вимоги
приватності). Сервіси мають розгортатися і змінюватися незалежно, а схема даних — бути відтворюваною в
dev, у тестах (Testcontainers) і в Kubernetes без ручних кроків. Потрібні транзакції ACID і обмеження
цілісності (`CHECK quantity >= 0`, унікальність платежу на замовлення).

## Розглянуті альтернативи

| Варіант | Переваги | Недоліки |
|---|---|---|
| A. Одна спільна БД для всіх сервісів | прості JOIN-и і звіти, одна транзакція на замовлення | сильна зв'язність через схему: зміна таблиці одного сервісу ламає інші; немає незалежного розгортання; персональні дані змішані з рештою |
| B. Одна БД, окрема схема на сервіс | менше контейнерів, ізоляція на рівні схем | спільна точка відмови і спільний ресурс; доступ «в обхід» API технічно можливий |
| C. **Окрема БД PostgreSQL на сервіс + Flyway** | слабка зв'язність, незалежні зміни схеми, ізоляція персональних даних у `user-db`, відтворюваність міграціями | більше контейнерів і пам'яті; немає JOIN-ів між сервісами; узгодженість лише через події (ADR-0002) |
| D. NoSQL (MongoDB) для каталогу | гнучка схема атрибутів рослин | другий рушій БД; втрата `CHECK`/FK; для курсу — зайва складність |
| E. Схема через `ddl-auto: update` або init SQL у контейнері БД | менше файлів | неконтрольовані зміни, немає історії версій, init-скрипти не виконуються на непорожньому томі |

## Рішення

Варіант **C**. Кожен бізнес-сервіс має власний контейнер PostgreSQL 16 і власну базу; Flyway під час старту
сервісу створює схему (`catalog`, `inventory`, `orders`, `payments`, `users`) і застосовує міграції
`src/main/resources/db/migration/V<n>__*.sql`. Hibernate працює з `ddl-auto: validate`, тобто перевіряє, але
ніколи не змінює схему. Застосовану міграцію не редагують — лише додають нову. Між сервісами зберігаються тільки
логічні ідентифікатори (`plant_id`, `order_id`) без зовнішніх ключів.

## Наслідки

- **Позитивні:** схема кожного сервісу версіонована в Git і однакова в dev, CI і k8s; зміна моделі одного
  сервісу не потребує координації з іншими; `user-db` можна копіювати, шифрувати і чистити окремо (право на
  забуття); перевірка відновлення однієї БД не зачіпає інші (`docs/lab-10/backup-drill.txt`).
- **Негативні:** 5 контейнерів БД (пам'ять ноутбука, 5 резервних копій); неможливі транзакції між сервісами —
  потрібна сага (ADR-0002); звіти через кілька сервісів збираються лише через API.
- **Обмеження для розробників:** нова таблиця або стовпець = новий файл `V<n>__*.sql`; відкат релізу можливий,
  лише якщо міграція сумісна зі старим кодом (ISD, розділ 7).
