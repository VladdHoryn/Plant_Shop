# ADR-0002: Сага замовлення як хореографія подій Kafka

| Поле | Значення |
|---|---|
| Номер | 0002 |
| Статус | **Accepted** (доповнено [ADR-0003](0003-synchronous-payment-read-for-tracking.md): синхронне читання платежу для трекінгу) |
| Дата рішення | 2026-10-14 (перша робоча версія, коміт `0207223`); оформлено як ADR 2026-11-14 |
| Автор / власник | VladdHoryn |
| Зачіпає | order-, inventory-, payment-, catalog-service; пакети `event`; `spring.json.type.mapping` у config-service |
| Залежить від | [ADR-0001](0001-database-per-service-postgresql-flyway.md): окремі БД виключають одну ACID-транзакцію на замовлення |

> Запис незмінний після прийняття. Заміна рішення — новий ADR, а цей отримує статус `Superseded`.

## Контекст

Оформлення замовлення зачіпає три сервіси з окремими базами (ADR-0001): склад має зарезервувати товар, платіжний
сервіс — провести оплату, сервіс замовлень — зафіксувати підсумок. Розподіленої транзакції немає. Платіж може
тривати і може бути відхилений (`payment.max-amount`); покупець не повинен чекати на весь ланцюжок у HTTP-запиті.
Потрібно: не втрачати кроки при перезапуску сервісу, компенсувати резерв при відмові оплати, переживати повторну
доставку повідомлень.

## Розглянуті альтернативи

| Варіант | Переваги | Недоліки |
|---|---|---|
| A. Синхронний ланцюжок REST (order → inventory → payment) | простий для читання код, одразу відома відповідь | часова зв'язність: недоступність будь-якого сервісу зриває замовлення; довгий HTTP-запит; компенсації вручну в коді order-service |
| B. Розподілена транзакція (2PC / XA) | атомарність | не підтримується Kafka + кількома PostgreSQL у Spring Boot без важкого менеджера транзакцій; блокування, погана доступність |
| C. Сага-**оркестрація**: order-service надсилає команди «зарезервуй», «спиши» і чекає відповідей | уся логіка процесу в одному місці, легко побачити стан | order-service стає «God Service», що знає API всіх учасників; більше топіків-команд |
| D. **Сага-хореографія**: кожен сервіс реагує на доменні події і публікує власні | слабка зв'язність, кожен учасник автономний, легко додати нового споживача (`plant-created` → inventory) | процес «розмазаний» по сервісах — потрібна документація потоку (SDD 2.1); складніше налагоджувати |
| E. RabbitMQ замість Kafka | простіші черги | немає журналу подій з повторним читанням; Kafka вже потрібна як шина подій |

## Рішення

Варіант **D** на Apache Kafka. Ланцюжок: `order-created` → inventory резервує → `inventory-reserved` /
`inventory-failed` → payment → `payment-completed` / `payment-failed` → order стає `CONFIRMED` / `CANCELLED`,
inventory списує або звільняє резерв. Синхронні Feign-виклики залишаються лише для **перевірок перед прийняттям**
замовлення (ціна з каталогу, наявність на складі), щоб покупець одразу отримав 400/409 замість скасування потім.

Правила:

1. Подію публікує `@TransactionalEventListener` — лише після commit транзакції БД (немає «фантомних» подій).
2. Кожен споживач ідемпотентний: повторна доставка ігнорується.
3. Ключ повідомлення — `orderId`, тому події одного замовлення йдуть в одну партицію по порядку.
4. Спільного модуля подій немає: кожен сервіс має свою копію record-класу, зіставлення — через
   `spring.json.type.mapping` у YAML config-service.

## Наслідки

- **Позитивні:** `POST /api/orders` відповідає одразу (202, `PENDING`); недоступність payment-service не губить
  замовлення — подія дочекається споживача; новий учасник додається підпискою без зміни order-service.
- **Негативні:** кінцева узгодженість — покупець має опитувати `GET /api/orders/{id}`; процес не видно в одному
  класі, тому SDD (розділ 2.1) — обов'язкова частина документації; перейменування події вимагає змін у всіх
  копіях record і в type mapping продюсера та споживачів.
- **Термінологія:** order-service **не оркеструє** сагу; формулювання «saga orchestration» у старому README було
  помилковим (Documentation Decay, `docs/lab-10/claim-verification.txt`, D1) і виправлене.
- **Пов'язані документи:** [SDD, розділи 2.1 і 5.3](../sdd.md#53-асинхронні-контракти-kafka).
