# ADR-0005: Контракт клієнтського API пишеться першим (API-first) в OpenAPI і є єдиним джерелом істини

| Поле | Значення |
|---|---|
| Номер | 0005 |
| Статус | **Accepted** |
| Дата рішення | 2026-11-22 |
| Автор / власник | VladdHoryn |
| Зачіпає | `docs/api/openapi.yaml`, `.spectral.yaml`, catalog-service і order-service (контролери клієнтського шляху), `scripts/doc-drift-check.sh` |
| Пов'язані | [ADR-0003](0003-synchronous-payment-read-for-tracking.md) (ендпоінт `/tracking` входить у контракт), [ADR-0004](0004-documentation-as-code-mkdocs.md) |

## Контекст

Схеми API досі існували лише як **code-first** довідка springdoc: вона генерується з анотацій запущеного сервісу,
тому описує те, що код робить, а не те, що обіцяно клієнтам. Зміна поля в DTO мовчки змінює «контракт»;
описів операцій, прикладів і узгодженого формату помилок немає; без запущеного сервісу довідки не існує.

## Розглянуті альтернативи

| Варіант | Переваги | Недоліки |
|---|---|---|
| A. Лише springdoc (code-first) | завжди відповідає коду, нуль ручної роботи | контракт = випадковий наслідок реалізації; ламаючі зміни непомітні; немає рев'ю контракту до коду |
| B. **OpenAPI-файл у репозиторії (API-first) для клієнтського шляху + springdoc для решти** | контракт рецензується в PR до реалізації; з нього генеруються довідка, SDK і contract-тести; лінтер Spectral | файл треба підтримувати; ризик дрейфу закривають drift-check і contract-тест |
| C. Генерувати серверні інтерфейси з OpenAPI (openapi-generator spring) | дрейф неможливий на рівні сигнатур | переписування контролерів усіх сервісів; згенерований код ускладнює Lombok/record-стиль проєкту |

## Рішення

Варіант **B**. `docs/api/openapi.yaml` (OpenAPI 3.0.3, `info.version` за SemVer) — єдине джерело для операцій
клієнтського шляху: пошук і картка рослини, створення, перегляд і список замовлень, трекінг. Звідси:

- довідка `docs/api/reference.md` рендериться Swagger UI безпосередньо з файлу (не копія);
- SDK генерується `openapi-generator` (`./scripts/api-sdk.sh`), а не пишеться вручну;
- якість контракту перевіряє Spectral (`.spectral.yaml`, поріг 0 errors);
- відповідність коду перевіряють `doc-drift-check.sh` (кожна операція контракту існує в контролері) та
  contract-тест Schemathesis проти запущеного gateway (`./scripts/api-contract-test.sh`).

Зміна клієнтського шляху починається зі зміни контракту в тому самому PR. springdoc лишається code-first
довідкою для внутрішніх і адміністративних ендпоінтів.

## Наслідки

- **Позитивні:** ламаючу зміну видно в diff контракту; клієнти отримують SDK і довідку однієї версії.
- **Негативні:** два джерела схем (контракт і springdoc) для 6 операцій — розбіжність між ними є дефектом,
  який ловить contract-тест.
- **Перегляд:** якщо контракт охопить більшість ендпоінтів, розглянути варіант C новим ADR.
