# ADR-0003: Синхронне читання платежу для трекінгу замовлення

| Поле | Значення |
|---|---|
| Номер | 0003 |
| Статус | **Accepted** |
| Дата рішення | 2026-11-14 (коміт `aef1513`; задокументовано в PASS-коміті Lab 10) |
| Автор / власник | VladdHoryn |
| Зачіпає | order-service (`PaymentClient`, `OrderTrackingService`, `OrderTrackingController`); `docker-compose.yml` |
| Доповнює | [ADR-0002](0002-kafka-choreography-saga.md) — не замінює його: сага лишається хореографією |

## Контекст

Щоб дізнатися результат замовлення, клієнт робив два запити: `GET /api/orders/{id}` і
`GET /api/payments/order/{orderId}`, і сам зводив відповіді. ADR-0002 дозволяє синхронні виклики лише для
перевірок перед прийняттям замовлення. Потрібна одна точка «де моє замовлення», не змінюючи саму сагу.

## Розглянуті альтернативи

| Варіант | Переваги | Недоліки |
|---|---|---|
| A. Залишити два запити на клієнті | без змін у сервісах | клієнт знає внутрішню будову (два сервіси), дублює логіку зведення |
| B. **order-service читає платіж синхронно (Feign) лише для трекінгу** | одна відповідь, мінімум коду, джерело істини — payment-service | нова синхронна залежність order → payment; при недоступності payment трекінг повертає 503 (саме замовлення працює) |
| C. order-service зберігає копію статусу платежу з подій `payment-*` | немає синхронної залежності, швидке читання | зміна схеми `orders` (міграція), дублювання даних, ризик розсинхрону; більше коду |
| D. Агрегація в api-gateway (BFF) | сервіси не змінюються | логіка в шлюзі на WebFlux, який зараз лише маршрутизує |

## Рішення

Варіант **B**. Це **запит на читання**, а не крок саги: order-service не змінює стан за результатом виклику і не
надсилає команд. 404 від payment-service трактується як `NOT_STARTED` (сага ще не дійшла до оплати). У
`docker-compose.yml` order-service стартує після того, як payment-service став healthy (додано healthcheck
порту 8084).

## Наслідки

- **Позитивні:** клієнт отримує стан замовлення і платежу одним запитом; контракт саги не змінився.
- **Негативні:** порядок запуску змінено (ISD, розділ 5: order-service перейшов у хвилю 4); payment-service став
  залежністю order-service для трекінгу — його недоступність дає 503 на `/tracking`.
- **Перегляд:** якщо навантаження на трекінг зросте, розглянути варіант C новим ADR, який замінить цей
  (`Superseded by ADR-NNNN`).
